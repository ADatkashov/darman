# Deploying the backend to Render (compute) + Neon (PostgreSQL)

Files: [`render.yaml`](../render.yaml) (Blueprint), [`backend/Dockerfile`](../backend/Dockerfile), [`backend/docker-entrypoint.sh`](../backend/docker-entrypoint.sh).
Nothing here creates resources or contains secrets; you enter credentials in the Render/Neon dashboards.

## 1. Neon
1. Create a project; region **AWS Europe (Frankfurt) `aws-eu-central-1`** (matches Render `frankfurt`). Postgres 16 or newer.
2. Database `darman` and a dedicated role (not the owner/admin role used for the console). Neon supports `pg_trgm` (used for search); the migration runs `CREATE EXTENSION IF NOT EXISTS pg_trgm`, which the database owner role may do.
3. Open **Connect** and copy the **direct** (non-pooled) connection, i.e. the host *without* `-pooler`. Flyway holds a session-level lock during migrations, which a transaction pooler (PgBouncer) breaks.
4. Convert it to the three Render variables:

| Neon string `postgresql://USER:PASSWORD@ep-xxx.eu-central-1.aws.neon.tech/darman?sslmode=require&channel_binding=require` | Render variable |
|---|---|
| `jdbc:postgresql://ep-xxx.eu-central-1.aws.neon.tech/darman?sslmode=require` (drop credentials and `channel_binding`) | `DARMAN_DB_URL` |
| `USER` | `DARMAN_DB_USER` |
| `PASSWORD` | `DARMAN_DB_PASSWORD` |

Notes: free-tier computes suspend when idle, so the first request after a pause is slow (pool `connection-timeout` is 30 s, `max-lifetime` 4 min so stale connections are recycled). The pool is limited to 5 connections to stay within Neon's limits; raise it with the plan.

## 2. Render
1. Push the repo (the Blueprint is `render.yaml` in the root) → **New → Blueprint** → pick the repo/branch `main`.
2. Fill the prompted variables: `DARMAN_DB_URL`, `DARMAN_DB_USER`, `DARMAN_DB_PASSWORD` (others marked `sync: false` can stay empty for a demo).
   `DARMAN_JWT_SECRET`, `DARMAN_PAYMENT_WEBHOOK_SECRET`, `DARMAN_DEMO_PASSWORD` are generated by Render.
3. Deploy. Render builds the Docker image, runs Flyway against Neon on startup and waits for `/actuator/health/readiness`.
4. Verify: `https://<service>.onrender.com/actuator/health` → `UP`; `/swagger-ui.html`; staff panel `/admin`.
   Demo accounts (phone list in the README) use the generated `DARMAN_DEMO_PASSWORD` (Dashboard → Environment).
5. Mobile app: `flutter build apk --dart-define=API_BASE_URL=https://<service>.onrender.com` (HTTPS is provided by Render).

**Persistent disk**: prescription files live on the 1 GB disk mounted at `/data/private-storage` (survives deploys; a service with a disk cannot scale to several instances and redeploys incur a short downtime). The entrypoint fixes ownership of the root-owned mount, then runs the app as an unprivileged user. Without a disk (free plan) uploaded prescriptions disappear on every deploy — acceptable for a throwaway demo only. For real use, implement an S3-compatible `FileStorage` adapter instead.

## 3. Going to production (`SPRING_PROFILES_ACTIVE=prod`)
`prod` refuses to start with demo adapters, and seeds **no** catalog and **no** accounts. Before switching, complete the checklist in `openspec/08-security-privacy.md`, then:
1. Set `DARMAN_API_DOCS_ENABLED=false`, `DARMAN_PRIVACY_URL`, `DARMAN_TERMS_URL`, `DARMAN_SUPPORT_PHONE`; keep the generated JWT/webhook secrets.
2. Configure a real SMS gateway (`DARMAN_SMS_GATEWAY_URL`, `DARMAN_SMS_API_KEY`) and a `PaymentProvider` (see `docs/integrations.md`).
3. Use a **fresh** Neon database/branch (the demo catalog is in the same schema; do not point `prod` at demo data). Flyway on `prod` applies only `db/migration`.
4. Bootstrap the first admin once (Neon SQL editor), then manage staff in `/admin`:
   ```bash
   htpasswd -bnBC 11 "" 'a-long-unique-password' | tr -d ':\n' | sed 's/^\$2y/\$2a/'   # prints the BCrypt hash
   ```
   ```sql
   INSERT INTO users (phone, full_name, password_hash, role_code, status, phone_verified_at, privacy_consent_at)
   VALUES ('+77XXXXXXXXX', 'Admin', '<hash>', 'ADMIN', 'ACTIVE', now(), now());
   ```
5. Load pharmacies, products, offers and sourced product information through the admin API/panel.
6. Neon: enable IP allow-listing if your plan supports it, use branch-based backups/point-in-time restore, and restrict the role to the `darman` database.

## Troubleshooting
| Symptom | Cause / fix |
|---|---|
| `Unable to obtain connection`, SSL errors | URL must start with `jdbc:postgresql://`, include `?sslmode=require`; no `channel_binding` |
| Flyway lock/timeout | Using the `-pooler` host → switch to the direct host |
| Deploy "no open ports" | App reads `PORT` (Render sets 10000) — don't override `server.port` |
| `Demo adapters must be disabled when the 'prod' profile is active` | Intended guard; unset demo flags or use profile `demo` |
| Slow first request after idle | Neon compute resumed from suspend; keep-alive or a paid always-on compute |
| 403 on file write at startup | Ensure a disk is attached; the entrypoint needs to start as root to `chown` the mount |
